# PM Ops Map: Site Walkthrough

This walkthrough follows the application from the first browser request to the main operator workflows. It is written for a collaborator reviewing the repository, a recruiter evaluating the build, or a future maintainer trying to answer, “Where does this screen come from?”

## The product in one minute

PM Ops Map is a local-first operating workspace for small property-management teams. It starts with 262 editable responsibilities across 17 departments, then lets an operator assign ownership, monitor task state, coordinate maintenance, track a lightweight portfolio, and export the resulting operating model.

The default app is static: there is no required account, database, or hosted API. Browser state is stored in `localStorage`. A separate Express service under `server/` is optional and only participates after a user explicitly connects Team Sync.

## Runtime map

```text
index.html
   │ loads
   ▼
js/app.js ── fetches config.json ──► js/state.js
   │                                  shared in-memory objects
   ├── hydrates saved browser data through js/storage.js
   ├── renders the selected screen through js/views/*
   ├── derives guidance through js/launchPlan.js
   └── optionally exchanges validated snapshots through js/sync.js
                                              │
                                              ▼
                                      server/src/app.js
                                              │
                                              ▼
                                      server/src/store.js
```

## 1. The browser shell: `index.html`

[`index.html`](../../index.html) provides the durable page structure:

- the header, stats, filters, and five navigation tabs;
- empty containers for Tracking, Map, Team, Work Orders, and Portfolio views;
- onboarding, work-order, import-review, notes, custom-field, backup, and sync modals;
- inline event attributes such as `onclick="switchView(...)"`; and
- the final ES-module entry tag for [`js/app.js`](../../js/app.js).

The feature screens are not separate routes. This is a single-page interface in which [`switchView`](../../js/app.js) hides every `.view-panel`, activates one panel, and asks the relevant renderer for fresh markup. That choice keeps deployment simple, but it also means HTML handler names and their `window` bindings must stay synchronized.

## 2. Bootstrap: `js/app.js`

[`js/app.js`](../../js/app.js) is the composition root. It imports the state, persistence, UI, view, import/export, launch-plan, handbook, recurring-template, and sync modules.

On `DOMContentLoaded`, it chooses one of two configuration paths:

1. A production bundle can provide `window.__PM_OPS_CONFIG__`. Webpack injects this value so a downloaded `dist/index.html` works over `file://`.
2. Source and hosted builds fetch [`config.json`](../../config.json) over HTTP.

`bootstrapWithConfig` then:

1. places `orgData`, `defaultAffinities`, and `ownerColors` in [`js/state.js`](../../js/state.js);
2. stamps every starter task with `_configName`, a stable identity that survives user-visible renames; and
3. calls `initApp`.

`initApp` deliberately hydrates saved data before rendering. Team, work orders, portfolio, audit entries, and task edits are loaded first; only then are Tracking, Launch Plan, stats, filters, legend, portfolio, notifications, and optional sync initialized. A returning user gets the saved company name. A first-time user gets onboarding.

At the bottom of the file, `Object.assign(window, ...)` exposes imported functions to the inline handlers in `index.html` and markup generated by view modules. If a click renders correctly but does nothing, this binding table is one of the first places to inspect.

## 3. The shared state: `js/state.js`

[`js/state.js`](../../js/state.js) holds the live objects used across screens:

- `orgData`: departments and tasks loaded from configuration;
- `teamData`: employees, badge colors, and department affinities;
- `workOrders`: maintenance records;
- `portfolio`: properties, tenants, and vendors;
- `auditLog`: up to 500 recent operating changes;
- `currentView`, `mapState`, and undo/color UI state; and
- status, priority, work-order, and audit-label constants.

The app uses shared mutable objects rather than Redux, a framework store, or an event bus. A feature updates an object, calls the matching persistence function, and redraws the affected views. This is direct and easy to deploy, but maintainers must remember to persist and refresh every downstream surface after a mutation.

## 4. Persistence and recovery: `js/storage.js`

[`js/storage.js`](../../js/storage.js) is the browser persistence boundary. It owns the `localStorage` keys, reloads saved task state into the current configuration, persists team/work-order/portfolio/audit changes, and manages five rolling backup snapshots.

Task restoration is identity-aware. The visible task name is editable, so a saved task is matched back to the current starter task with `_configName`, not only the displayed name. Unsupported values are normalized: status and priority must be in their allowed cycles, note and custom-field sizes are capped, and malformed collections fall back safely.

Before risky bulk replacements—imports, auto-assignment, and remote sync—the app records a backup. JSON import also has a one-step in-memory undo path in [`js/io.js`](../../js/io.js).

## 5. First-run journey: onboarding to Launch Plan

The onboarding modal in [`index.html`](../../index.html) collects the company name, approximate portfolio size, and operating focus. [`submitCompanyName`](../../js/ui.js) stores those preferences, applies them to the page, and refreshes the Launch Plan.

[`js/launchPlan.js`](../../js/launchPlan.js) turns current state into an operator-facing setup dashboard. It derives:

- the next recommended action;
- setup and data-quality gaps;
- critical coverage areas;
- a focus-specific seven-day plan;
- risks such as unowned tasks, unassigned work orders, expiring leases, and delinquency; and
- a readiness score.

The file is intentionally a derived-view layer: `renderLaunchPlan` reads current state but should not mutate it. Guided buttons route the user to the relevant tab or modal.

For evaluation without real data, [`buildDemoWorkspace`](../../js/templates.js) supplies a fictional team, assignments, portfolio records, and work order. “Show me an example first” loads that data into the same real workflows; it is not a separate mock UI.

## 6. Core journey: map responsibilities and track execution

[`js/views/tracking.js`](../../js/views/tracking.js) renders each configured department as a collapsible task list. An operator can:

- rename a responsibility;
- change owner, status, priority, or due date;
- link a blocking task;
- attach notes and up to ten custom fields;
- filter by text, owner, status, and priority; and
- apply owner or status changes in bulk.

Each mutation follows the same practical sequence: validate the input, update `orgData`, save through `storage.js`, record an audit event where applicable, update the affected DOM or rerender, and refresh global counters/beacons.

The Tracking tab is the system of record for responsibility ownership. The other primary views are alternative projections or adjacent operating records.

## 7. Visual journey: see the organization as a flow map

[`js/views/map.js`](../../js/views/map.js) builds an SVG directly from current departments, task ownership, and workload. It draws company-to-department and department-to-owner relationships, scales line weight by task count, and provides hover/click details.

There is no charting dependency. Small SVG helper functions create groups, paths, lines, circles, rectangles, and text nodes. The map therefore stays lightweight and fully derived from the same live `orgData` shown in Tracking.

## 8. Staffing journey: build the team and distribute ownership

[`js/views/team.js`](../../js/views/team.js) manages employees, colors, department affinities, role templates, workload bars, playbooks, and the audit-log modal.

The most important workflow is `runAutoAssign`:

1. stop if no unowned tasks exist or no employees are available;
2. create a recovery snapshot and undo snapshot;
3. calculate each employee’s current assigned-task count;
4. for every unowned task, prefer employees whose affinities include its department;
5. if nobody matches, use the whole team as a fallback;
6. sort candidates by current workload, assign the least-loaded candidate, and immediately increment that workload; and
7. persist, rerender, audit, and report departments that required fallback.

The result is deterministic for the current employee order when workloads tie. It balances task counts, not effort estimates, skill levels, schedules, or urgency. Those are intentional current limitations rather than hidden capabilities.

## 9. Maintenance journey: intake to completion

[`js/views/workorders.js`](../../js/views/workorders.js) renders a four-column board: Submitted, Scheduled, In Progress, and Completed. The modal captures property, unit, resident, issue, notes, priority, assignee, vendor, target date, and estimated cost.

Creating or editing a work order validates required fields, normalizes values, persists the collection, writes an audit entry, and rerenders the board and beacons. `advanceWorkOrder` moves a card through the fixed lifecycle. [`js/views/recurring.js`](../../js/views/recurring.js) can generate batches from five built-in templates; it creates ordinary work orders, so generated work remains editable through the same board.

## 10. Portfolio journey: operational context around the work

[`js/views/portfolio.js`](../../js/views/portfolio.js) manages three lightweight record types:

- properties, including address, unit count, owner, and an external document URL;
- tenants, including property, contact details, rent, lease dates, balance, payment date, and document URL; and
- vendors, including trade, contact details, coverage, and document URL.

The screen derives lease and delinquency signals with helpers from [`js/utils.js`](../../js/utils.js). Payment recording reduces a tenant balance and adds an audit entry; it is not a payment processor or accounting ledger. CSV imports are append-only, map tolerant header names, show skipped/warning summaries, and do not update or delete existing records.

## 11. Data portability and generated proof

[`js/io.js`](../../js/io.js) is the import/export boundary. It can export the full workspace as versioned JSON, export task/portfolio/work-order CSVs, copy state to the clipboard, and validate imported snapshots before showing a review modal.

[`js/stateSchema.js`](../../js/stateSchema.js) defines the schema marker and version, builds portable payloads, matches incoming departments/tasks to the current configuration, and reports incompatible or skipped data before application.

[`js/handbook.js`](../../js/handbook.js) turns the live workspace into Markdown or printable HTML. This is important product proof: the application does not only display an operating model; it can hand that model back to the team as an onboarding and SOP artifact.

## 12. Optional Team Sync

Team Sync is opt-in. [`js/sync.js`](../../js/sync.js) stores the connection settings locally and polls about every eight seconds.

On each tick it compares the current serialized snapshot with the last synchronized snapshot:

- local changes trigger a version-checked push;
- no local changes trigger a cheap remote version check, followed by a pull only when needed;
- a stale push receives HTTP `409` plus the current remote state and opens the same validated import-review flow used by file imports; and
- an uncontested newer remote snapshot is validated, backed up, added to undo history, and then applied.

The optional service is composed of [`server/index.js`](../../server/index.js), [`server/src/app.js`](../../server/src/app.js), and [`server/src/store.js`](../../server/src/store.js). It exposes health, pull, version, and push endpoints. Each workspace is one JSON file protected by an scrypt-derived passphrase hash. Optimistic versions prevent silent lost updates, while an in-process per-workspace promise lock serializes concurrent writes.

This is suitable for a small trusted team or product trial, not enterprise multi-tenant collaboration. There are no user accounts, role-based permissions, field-level merging, database transactions, password recovery, or horizontal coordination between multiple server instances.

## Where to start changing the code

- Change starter departments or responsibilities in [`config.json`](../../config.json).
- Change startup order or add a new main screen in [`js/app.js`](../../js/app.js).
- Change a screen inside its matching file in [`js/views/`](../../js/views/).
- Change browser persistence or backups in [`js/storage.js`](../../js/storage.js).
- Change portable workspace compatibility in [`js/stateSchema.js`](../../js/stateSchema.js) and its tests in [`js/__tests__/stateSchema.test.js`](../../js/__tests__/stateSchema.test.js).
- Change Team Sync behavior in [`js/sync.js`](../../js/sync.js) and the server contract under [`server/src/`](../../server/src/).

For the important symbols inside those files, continue with the [code glossary](code-glossary.md).
